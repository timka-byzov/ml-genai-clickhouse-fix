# Kafka и ClickHouse

Домашка по ML/GenAI. Скрипт отправляет CSV в Kafka, а ClickHouse читает сообщения через Kafka engine и materialized view.

## Запуск

Нужен Docker Compose или Podman Compose. Скачать архив [teta-ml-1-2025](https://www.kaggle.com/competitions/teta-ml-1-2025/data) и распаковать `train.csv` в `data/`. Затем запустить:

```bash
./scripts/project.sh up
./scripts/project.sh run --csv data/train.csv
```

Скрипт создаёт таблицы и загружает CSV. После загрузки проверяет число строк, сверяет результат SQL и сравнивает время запросов. Результат сохраняется в `results/max_transaction_by_state.csv`, измерения в `results/benchmark.csv`.

Для задания из CSV берутся время, штат, категория и сумма. Скрипт понимает оба варианта названий столбцов: `transaction_time` / `trans_date_trans_time`, `us_state` / `state`, `cat_id` / `category`, `amount` / `amt`. Если часовой пояс не указан, время считается UTC. `row_id` содержит номер строки CSV, начиная с 1. Для денег используется `Decimal(18, 2)`.

При одинаковых максимальных суммах выбирается последняя строка CSV. Результат SQL сверяется с расчётом в Python.

## Файлы

- `scripts/csv_to_kafka.py`: загрузка CSV в Kafka отдельным скриптом.
- `sql/01_schema.sql`: базовая таблица и Kafka engine.
- `sql/02_schema_optimized.sql`: оптимизированные таблицы и materialized views.
- `sql/03_max_transaction_by_state.sql`: итоговый запрос.
- `sql/05_max_transaction_by_state_baseline.sql`: тот же запрос без предварительной агрегации.
- `sql/06_max_transaction_by_state_optimized_raw.sql`: запрос по оптимизированной таблице без агрегации.

В оптимизированной таблице используются `LowCardinality`, сжатие ZSTD и сортировка по штату. Состояние `argMax` хранится отдельно в `AggregatingMergeTree`, поэтому итоговый запрос читает агрегированные данные вместо всех транзакций. Базовая таблица нужна для сравнения.

Бенчмарк прогревает три запроса, затем пять раз повторяет их по очереди. Query cache отключён, используются два потока. В CSV сохраняются время, прочитанные строки и байты, а также память из `system.query_log`. Размер таблиц берётся из `system.parts`.

## Другие команды

```bash
./scripts/project.sh benchmark
./scripts/project.sh sql sql/04_validation.sql
./scripts/project.sh export sql/03_max_transaction_by_state.sql results/max_transaction_by_state.csv
./scripts/project.sh down
```

Повторный `run` с тем же файлом использует уже загруженные данные. Для другого файла или другого `--limit` нужна отдельная загрузка: скрипт сам данные не очищает. `producer` при каждом запуске отправляет строки заново. Kafka engine может повторно доставить сообщения при сбое.

Адрес Kafka: `localhost:9092`. ClickHouse доступен на `localhost:8123` и `localhost:9000`. База `homework`, пользователь и пароль `student`. Порты можно поменять через `.env.example` → `.env`. Данные в томах сохраняются после `down`.

## Результаты

Проверка выполнена на полном `train.csv`: 786 431 транзакция, 51 значение штата, 14 категорий. В обеих таблицах число строк и уникальных `row_id` совпало с CSV. Все три SQL-запроса вернули одинаковый результат, который совпал с расчётом в Python.

Медианы пяти прогретых запусков на macOS ARM64 / Podman:

| Запрос | Время, мс | Прочитано строк | Прочитано байт |
| --- | ---: | ---: | ---: |
| Базовая таблица | 43 | 786 431 | 27 149 715 |
| Оптимизированная таблица | 42 | 786 431 | 14 159 492 |
| Предварительная агрегация | 1 | 250 | 36 790 |

Базовая таблица занимает 14 748 407 байт. Оптимизированная вместе с агрегатной занимает 6 064 111 байт. В стенде оставлены обе версии для сравнения. Сортировка и новые типы почти не изменили время полного `GROUP BY`. Итоговый запрос ускорился за счёт предварительной агрегации. Измерения каждого запуска находятся в `results/benchmark.csv`.
